## 1. 현재 수량과 검수 자료

`일주론`3글과 `현묘의 사주 이야기`1글은 보존된 yavares 도메인의 같은 저자 묶음으로 취급한다. 서로 다른 책자명/글4개를 독립4저자 지지로 세지 않는다. `명리학탐구(고급1)`3글은 동일 모음집이며 저자 실명·원출처 계보가 미확정이다. 독립 지지 수는null이다. 이 구분은 원문의 성향·건강·직업 주장을 사실로 인증하지 않는다.

## 3. 실제 조립 경로 측정

`report.js`는 증류본이 있으면 그대로 선택하고 명시 현침 관련 문장만 기존 정책으로 보류한다. `saju.ts`는 핵심/첫 성격의 대화 출처와 일주 카드 마지막 블록에 `sources[0]`을 붙인다. 카드 각 문장이 그 첫 출처에서 왔다는 검증은 없다. 견해 문자열에는 각src가 남지만 문장별 검증 위치는 없다.

[소비 측정](data/basic_sentence_consumers.json)은 실제 빌드KB와 Vite로 원래 함수를 실행한다. 세 일주를 만드는 합성 날짜별 남녀6입력에서 검토14항목이 원문 조건의 충족 여부를 계산하지 않은 채 그대로 일주 카드에 전달됨을 확인했다. 이는 입력→데이터 경계의 재현이며 화면/LLM 상담/개인정확도 측정이 아니다. 미상1입력은 기존 공통보류로 일주카드가 없다.

발췌 대체경로도 메모리에서 갑자 증류본 하나만 잠시 제외해 재현했다. 실제 색인 순서는 고급1#0017→일주론#0001이며, 증류 sources 순서와 반대다. 앞6문단은 각각 제목/목차·도입문이다. 엔진에는 이 발췌가 생기지만 현재 `toReading`의 일주 분기는 증류본을 요구하므로 일주 카드/대화에는 표시되지 않는다. 현60개 증류가 모두 있는 정상경로에서 인사말이 보인다고 보고하지 않는다. 첫 측정은 증류 출처 순서를 발췌 순서로 가정해 실패했고, 실제 색인과 양쪽 원문을 확인하여 측정만 고쳤다.

## 4. 재현과 검증

```bash
python3 docs/knowledge-model/basic_sentence_review.py --check
python3 docs/knowledge-model/basic_sentence_review.py --item IN05
python3 -m unittest discover -s docs/knowledge-model -p 'test_basic_sentence_review.py'
# 실제 빌드KB/앱 의존성 준비 뒤:
node docs/knowledge-model/measure_basic_sentence_consumers.mjs --check
npm run verify
```

조회기는 전체 검토판의 canonical JSON을 고정하고 실제60초안·색인·카탈로그·소비코드의 LF정규화 해시와 DOCX 원바이트 해시를 확인한다. 문장/견해를 바꿔치기하거나 조건·계보·개인적격을 승격하면 거부한다. 이는 기록 무결성 검사이며 의미의 자동 판정이 아니다. 새 출처/코드 판본을 검수하면 별도 기록/명시적 판본 갱신이 필요하다. 과거 감사 해시를 조용히 갱신하지 않는다.

신규 Python9검사는 필수 discover에 포함된다. 실제 사본의 DOCX/초안 변조와 추가파일·실제CRLF, 조건/견해/출처/계보 변경, 문맥 포함 조회, 다른cwd/ASCII 콘솔·경로탈출·읽기전용을 확인한다. 소비 측정 `--check`는 별도로 실행하며 Python9검사만 통과했다고 실제 앱 측정 성공으로 세지 않는다.

착수 전체8게이트는 Python251·앱17·실제 Chromium까지 통과했다. 새9검사는 초기 괄호 문법 오류를 수정한 뒤 통과했고, 소비 측정은 위 순서 가정 오류를 교정한 뒤 통과했다. 최종 전체검사·검토·원격head·병합 상태는 해당 PR 영수증을 따른다.

## 6. 다음 첫 작업
