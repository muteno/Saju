# 기본 풀이를 먼저 갖추는 보강 계획

기준: 2026-09-22 사용자 원문 13. 자료량·코드 실행과 해석 알고리즘 완성은 구별한다. 이 계획은 문맥 조건부 지식망이라는 장기 목표 아래 첫 사용 가능한 결과를 일주 설명과 기본 성향 풀이로 정한다.

## 추가 기준 자료 — 사용자 원문 14

Figma 보드의 기초 개념 체계를 먼저 확인하고 기존 블로그 정의와 대조한다. 그 결과를 일간·일지·십신과 일주 풀이의 공통 개념층으로 사용한다. 보드의 본문 수집 상태와 기존 저장소 자료의 대응은 `FIGMA_FOUNDATION.md`에서 관리한다. 미확인 화면 글자나 연결선을 뜻이 확인된 규칙으로 채우지 않는다.

## 현재 재사용 가능한 재료

| 확인한 것 | 범위 | 확인의 한계 |
|---|---:|---|
| 첨부 블로그 `일주론 글모음` | 본문 61글: 60일주 + 입문 1글 | 목차를 제외한 본문 제목 집계, 문장 의미 검수는 별도 |
| `천간과 지지 글모음` | 본문 28글 | 개별 정의와 해석 조건을 구분해야 함 |
| `십신과 합충 글모음` | 본문 59글 | 동반 조건·예외·저자 관점을 보존해야 함 |
| 기존 `dosa-app/kb/distilled/ilju/` | 60개 JSON, 성격 문장 초안 402개 | 파일 존재는 검수 완료나 해석 정확도 증명이 아님 |
| 기존 일주 색인 | 60키, 연결된 고유 글 97개 | 관련성·출처 독립성·요약 충실도는 별도 확인 |

상세 집계 방식·파일 경로·품질 갭은 [basic_reading_findings.json](basic_reading_findings.json)에 기록했다.

현재 앱에도 `buildReading → buildReport → toReading` 경로가 있다. `dosa-app/engine/src/report.js`에서 자료를 조회하고 `app/src/data/saju.ts`에서 일주 핵심·성격·관점차이를 화면에 연결한다. 이 경로를 출발점으로 삼을 수 있다. 엔진 원본은 `dosa-app/engine/src/`이며 앱 vendor 파일을 직접 수정하지 않는다.

## 첫 제품 목표

입력된 원국에 대해 다음 네 항목을 근거와 함께 출력한다.

1. **기본 구조 설명:** 일주·일간·일지 및 필요한 기초 관계가 무엇인지.
2. **기본 성향 후보:** 문헌이 설명하는 경향과 그 적용 범위. 특정 단어만으로 개인을 확정하지 않는다.
3. **원국에 따른 조정:** 이미 확인된 다른 요소가 어떤 문헌 조건과 관련되는지. 확인되지 않은 조정은 만들어내지 않는다.
4. **근거와 미상:** 문장별 출처, 다른 관점, 입력 부족으로 판단할 수 없는 부분.

초기 완성 기준은 읽을 수 있는 기본 풀이의 품질이다. 학습·보정되지 않은 퍼센트를 채워 넣는 것을 필수 목표로 삼지 않는다. 이후 이 문장·조건 구조를 조건부 관계 모델의 학습 자료로 이어간다.

## 구현 순서와 완료 기준

| 단계 | 수행할 작업 | 완료 기준 |
|---|---|---|
| 1. 기존 60일주 검수 | 요약 문장을 원문 구간에 묶고 주장·조건·예외·반론을 분리 | 60일주마다 기본 설명과 성향 후보의 근거를 찾을 수 있고 미확인은 보류됨 |
| 2. 기초 관계 연결 | 일간 10·일지 12·십신 10의 정의와 해석 주장을 구분 | 같은 용어라도 문맥·저자에 따른 차이를 덮어쓰지 않음 |
| 3. 기본 풀이 출력 | 기존 앱 조립 경로를 활용해 네 항목을 출력 | 인사말·목차 발췌, 무근거 문장, 첫 출처만 대표 부착하는 문제를 점검 |
| 4. 원국 문맥 보강 | 월령·위치·다중 상호작용의 조건을 추가 | 입력 변화에 따라 무엇이 바뀌었는지 원문까지 추적 가능 |
| 5. 대운·세운 확장 | 원국의 기본 설명과 시기별 조건을 별도 계층으로 적층 | 시기 맥락과 원국 사실이 섞이지 않고 시간 정보 누수가 없음 |
| 6. 확률 학습·보정 | 검수된 문맥 사례와 별도 관측 라벨로 기준 모델 비교 | 추가 변수·자료가 실제 평가에서 개선했는지 보고 |

한꺼번에 60개 요약을 새로 쓰기 전에, 기존 요약의 서로 다른 오류 유형을 대표하는 작은 묶음에서 검수·출력 형식을 확인한다. 형식이 정해지면 60일주 전체에 같은 기준을 적용한다. 작은 묶음 통과를 전체 완료로 보고하지 않는다.

## 계속 들어오는 스크래핑 자료를 반영하는 방식

원본 식별·해시 → 글과 저자 집단 분리 → 기존 자료와 중복 확인 → 주장·조건·예외·반론 추출 → 출처 검수 → 기존 개념·관계에 연결 → 평가 후 풀이 반영.

새 자료는 기존 주장을 지지할 수도, 적용 범위를 좁힐 수도, 새로운 조건이나 반론을 제시할 수도 있다. 새로운 글을 무조건 기존 결론의 지지 표로 세지 않는다. 같은 저자의 글·영상·재인용은 계보를 묶고, 이전 자료와의 차이를 남긴다. 검수되지 않은 새 자료를 기존 검증 내용을 덮는 데 바로 사용하지 않는다.

주장 카드에는 최소한 다음을 저장한다: 개념·관계, 원문 구간, 저자 집단, 원국/시기 범위, 필요한 조건, 완화·반대 조건, 미확인 정보, 검수 상태, 변경 이력. 사용자 설명의 예시는 카드의 정답 근거가 아니다.

## 먼저 확인할 현재 품질 갭

- 기존 성격 문장은 배열 형태여서 문장별 원문 구간·조건 연결이 부족하다.
- `toReading`은 복수 출처가 있는 요약에도 첫 출처를 대표로 부착하는 경로가 있다. 문장과 출처의 대응을 검토해야 한다.
- 일주 요약을 읽을 수 있는 상태와 원국 전체에 맞게 조건을 조정한 상태를 구분해야 한다.
- 생시 미상 시 출력 숨김과 내부 계산에서의 미상 처리가 같은 범위를 보장하는지 확인해야 한다.
- 기존 보드 강약 점수·운세 가감점은 정책값이다. 학습된 관계 확률로 이관하지 않는다.
- 인용문이 원문과 같다는 검증만으로 요약의 의미, 조건 누락, 개인에 대한 해석 정확도가 검증되지는 않는다.

## 현재 상태

이 문서는 원문과 현재 코드를 읽고 만든 개발 계획이다. 이번 저장소 편입에서 앱의 풀이 기능이나 60일주 문장들을 변경하지 않았다. 실행·학습 시제품은 [CURRENT_STATE.md](CURRENT_STATE.md), 장기 설계는 [PROJECT_AGENDA.md](PROJECT_AGENDA.md)를 함께 참조한다.
