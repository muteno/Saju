### 4-1. ★가산합성(밀도 발광) — `globalCompositeOperation = 'lighter'`

**무엇인가 (쉬운 말):** 선을 겹쳐 그릴 때 색을 "덮어쓰기" 대신 "더하기"로 합친다. 그래서 선이 100개 겹친 자리는 10개 겹친 자리보다 정확히 10배 밝다. **밝기가 곧 밀도가 된다.** 운영자 이미지 1번의 하얀 발광이 이것이다.

**Canvas 2D로 되나 → 된다. 한 줄이다.** `[확인]`
```js
ctx.globalCompositeOperation = 'lighter';   // 겹치면 더해진다
// … 선 다 긋고 …
ctx.globalCompositeOperation = 'source-over';  // 원복
```
- MDN: *"lighter — 겹치는 부분에서 색상 값을 더해 색을 결정한다"* — [MDN globalCompositeOperation](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/globalCompositeOperation)
- 참고: [Konva Blend Mode 문서](https://konvajs.org/docs/styling/Blend_Mode.html) · [zetcode 튜토리얼](https://zetcode.com/canvas-api/globalcompositeoperation/)

**실측 증명 1 — 진짜로 밀도가 밝기가 되나?** `[실측]`
흰 선 알파 0.002, 화면 중앙 200×100 영역의 밝기(R값, 배경 = 14):
```
간선 전량(21,869) 그렸을 때   평균 58.9   (배경 뺀 순수 신호 44.9)
간선 절반(10,934) 그렸을 때   평균 36.3   (배경 뺀 순수 신호 22.3)
                                          → 22.3 × 2 = 44.6 ≒ 44.9
```
**밝기가 간선 개수에 정확히 비례한다. 발광 = 밀도가 수학적으로 성립한다.**

**실측 증명 2 — 왜 그냥 반투명(source-over)으로는 안 되나?** `[실측]`
```
같은 알파 0.002 로
  source-over : 화면 밝기 14 (= 배경 그대로. 선이 아예 안 보인다)
  lighter     : 화면 밝기 14 → 242 (다이내믹 레인지 다 씀)
```
**덮어쓰기 방식은 알파를 낮추면 8비트 반올림에 먹혀 사라지고, 알파를 올리면 밀집부가 통째로 회색으로 뭉개진다. 가운데가 없다.** 가산합성만이 "아주 흐린 선 × 아주 많이"를 표현할 수 있다.

**실측 증명 3 — 내가 처음에 틀렸던 것** `[실측, 자기 반증]`
나는 *"여러 선을 한 번의 `stroke()`로 배칭하면 그 안에서 겹친 건 가산이 안 될 것"*이라고 의심했다. **틀렸다.**
```
한 번에 stroke (K=0)   밝기 평균 58.9 / 최대 242
간선마다 stroke (K=1)   밝기 평균 58.9 / 최대 242
500개씩 stroke (K=500) 밝기 평균 58.9 / 최대 242
                        → 완전히 동일
```
**배칭해도 가산은 그대로 유지된다. 즉 성능(배칭)과 발광(가산)은 서로 안 싸운다.** 다행이다. 안 재보고 썼으면 이 문서가 틀린 설계를 권했을 것이다.

**비용** `[실측, 소프트웨어 래스터]`
| 그리는 것 | source-over | lighter | 배수 |
|---|---:|---:|---:|

| 백본 2,318 간선 | — | **73.8 ms** | |

**→ 가산합성은 공짜가 아니다. 전량 21,869개에 걸면 최악 조건에서 1.3fps다. 백본에 걸어야 산다.**

### 4-2. ★백본 필터 — 그릴 것을 줄인다 (삭제 아님)

**무엇인가 (쉬운 말):** 21,869개를 다 그리지 말고, **각 개념이 가장 강하게 붙은 것 몇 개만** 그린다. 지도에서 골목길을 다 지우고 큰길만 남기는 것과 같다.

**★헌법 위반 아님을 먼저 못 박는다.** 절대 원칙은 *"동시출현 간선 21,916개를 삭제하지 마라"*이다.
**이건 삭제가 아니라 '화면에 안 그리기'다.** 데이터는 그대로 있고, 옆으로 새어 나갈 다리도 그대로 있고, 슬라이더를 밀면 다시 보인다. 지금 화면도 이미 공기 층 기본값이 **꺼짐(0/21,869)**이다 `[실측, 지식망.html 상태표시줄]`.

**방법 A — 노드당 상위 k개만 (가장 쉽다)** `[실측 23:05]`
```
상위 3 만 남기면    709 간선 (원본의 3.2%)
상위 5 만 남기면  1,186 간선 (5.4%)
상위 10 만 남기면 2,318 간선 (10.6%)
상위 20 만 남기면 4,483 간선 (20.5%)
```
모든 노드가 자기 상위 k를 갖고 있으므로 **외딴 노드가 안 생긴다.** 구현 = 정렬 후 자르기, **약 10줄.**

**방법 B — 디스패리티 필터 (원칙 있는 방식, 논문 근거)** `[확인]`
> Serrano, Boguñá, Vespignani, *Extracting the multiscale backbone of complex weighted networks*, **PNAS 106(16), 2009**
> [PNAS 원문](https://www.pnas.org/doi/10.1073/pnas.0808904106) · [arXiv:0904.2389](https://arxiv.org/abs/0904.2389)

노드 i의 간선 중 j로 가는 비중 `p_ij = w_ij / Σw_i`, 노드 i의 차수 `k_i`일 때
```
α_ij = 1 − (k_i − 1) ∫₀^{p_ij} (1−x)^{k_i−2} dx
     = (1 − p_ij)^(k_i − 1)          ← 닫힌 형태
α_ij < α_임계  이면 남긴다 (권장 임계 0.05~0.20)
```
- 닫힌 형태는 [DerwenAI/disparity_filter 구현 코드](https://github.com/DerwenAI/disparity_filter)의 `get_disparity_significance` / `disparity_integral`을 받아 내가 손으로 정리·검산한 것이다 `[확인, 검산함]`
- 뜻: *"이 개념이 가진 다리들이 전부 똑같은 굵기라면 우연히 이만큼 굵을 확률"*. 낮을수록 진짜 신호.
- **핵심 장점: 척도를 안 정한다.** 다리 240개짜리 허브(`일간`)와 다리 6개짜리 변두리 개념에 같은 잣대를 쓰지 않는다. 단순 임계값(w>50 같은 것)은 허브만 살아남아 화면이 또 털뭉치가 된다.
- 구현 = **약 20~25줄.** 외부 의존 0.

**비용** `[실측, 소프트웨어 래스터, 무작위 표본으로 편향 제거]`
```

      0        0.2 ms        —       ← 고정비용은 사실상 0
    709       33.4 ms     62.0 ms
  1,186       59.3 ms    104.1 ms
  2,318       76.9 ms    149.6 ms

### 4-3. 계층 엣지 번들링(HEB) — 조건부 채택

**무엇인가 (쉬운 말):** 두 개념을 잇는 선을 직선으로 긋지 말고, **자기 서랍(중주제) → 자기 캐비닛(대주제) → 뿌리 → 상대 캐비닛 → 상대 서랍**을 거쳐 돌아가게 휘어 그린다. 같은 길을 지나는 선들이 자연히 다발로 뭉쳐 **줄기**가 된다. 지하철 노선도가 선을 겹쳐 그리는 것과 같다.

> Danny Holten, *Hierarchical Edge Bundles: Visualization of Adjacency Relations in Hierarchical Data*, **IEEE InfoVis / TVCG 2006**
> [논문 PDF (JHU 사본)](https://www.cs.jhu.edu/~misha/ReadingSeminar/Papers/Holten06.pdf) · [Semantic Scholar](https://www.semanticscholar.org/paper/e6987da6dc412f22ca5dd62da2affdcdd8e51d8e)
> 후속: Holten & van Wijk, *Force-Directed Edge Bundling*, **Computer Graphics Forum 28(3), 2009** — [Wiley](https://onlinelibrary.wiley.com/doi/abs/10.1111/j.1467-8659.2009.01450.x) · [구현 예 synesenom/fdeb](https://github.com/synesenom/fdeb)

**수식 (구현에 필요한 전부)** `[확인]`
1. 제어점 = **트리에서 두 노드를 잇는 경로**(공통 조상 제외)
2. 그 제어점들을 β로 직선 쪽으로 당긴다 —
```
P'_i = β·P_i + (1−β)·( P_0 + (i/(n−1))·(P_{n−1} − P_0) )
```
- β=1이면 완전히 휨(줄기 굵게 뭉침), β=0이면 그냥 직선. 관례값 **β=0.85**
- 이 수식은 [d3-shape의 `curveBundle` 소스](https://github.com/d3/d3-shape/blob/main/src/curve/bundle.js)에서 그대로 확인했다(`this._beta * x[i] + (1 - this._beta) * (x0 + t * dx)`) `[확인]`
- **d3를 쓰라는 게 아니다. 수식 한 줄만 베껴오면 된다.**
3. 휘어진 제어점을 균등 분할해 폴리라인으로 그린다(우리는 B-스플라인 대신 등간격 보간으로 충분)

**★실측 반전 — 번들링이 직선보다 빠르다** `[실측, 같은 간선·같은 순서]`
```
직선 21,869개                          380.2 ms
HEB  4분할 β=0.85  (87k 세그먼트)       235.5 ms   ← 세그먼트 4배인데 1.6배 빠름
HEB  8분할 β=0.85 (175k 세그먼트)       308.1 ms
HEB 16분할 β=0.85 (350k 세그먼트)       357.9 ms   ← 세그먼트 16배인데 직선보다 빠름
HEB  8분할 β=0.60 (더 세게 묶음)        233.5 ms   ← 세게 묶을수록 더 빠르다
HEB  8분할 β=0.95 (덜 묶음)             338.2 ms
```
**해석: 병목은 선의 개수가 아니라 화면에서 칠해지는 픽셀 넓이다.** 직선은 화면 전체에 흩뿌려져 넓게 칠하고, 번들은 줄기로 모여 좁게 칠한다. **번들링은 예뻐질 뿐 아니라 싸진다.** 이건 내가 예상 못 했던 결과다.

**★그런데 함정 — 번들링 + 가산합성은 폭발한다** `[실측]`
```
HEB 8분할 · source-over    308.1 ms
HEB 8분할 · lighter      3,447.2 ms   ← 11.2배
(직선 + lighter 는 1.29~1.38배에 그침)
```
**줄기 속에 잉크가 극도로 몰려서 겹침 처리 비용이 터진다. 두 기법을 동시에 켜지 마라.** 이 함정을 안 재고 합쳤으면 화면이 조용히 3초에 한 프레임이 됐을 것이다.

**우리 데이터 적합성 — 반반이다** `[실측, §3-3]`
- ✅ 대주제 교차 91.6% → 뿌리까지 올라가는 굵은 줄기가 실제로 생긴다
- ❌ **중주제쌍 1,310 / 최대 1,326 = 98.8% 포화** → 줄기 자체가 1,310가닥짜리 털뭉치가 된다
- **→ 번들링만 하면 "작은 털뭉치"가 될 뿐이다. 백본 필터를 먼저 걸어야 줄기 수가 줄어 의미가 생긴다.**

### 4-4. 3D force-directed 배치 — 이미 충분하다

- **그런데 우리는 노드 316개(개념 249 + 계층 허브 67)다.** 실측:
```
노드 316 · 순진한 O(n²) 척력(49,770쌍) + 인력, 3D
  1회 반복             0.51 ms      ← 60fps 한 프레임에 32회 반복 가능
  300회 반복(수렴)      153 ms      ← 화면 뜨기 전에 이미 끝난다

### 4-6. 원근 투영 직접 구현 — 이미 다 돼 있다

**필요한 것 전부:**
```js
// 1) 회전 (yaw·pitch)  — 4x4 행렬을 안 만들고 성분만 써도 된다
x1 = x*cos(yaw) + z*sin(yaw);   z1 = -x*sin(yaw) + z*cos(yaw);
y2 = y*cos(pitch) - z1*sin(pitch);  z2 = y*sin(pitch) + z1*cos(pitch);
// 2) 원근 나눗셈 — 이 한 줄이 원근의 전부다
w  = FOV / (FOV + z2);        // 멀수록 w 작아짐
sx = x1*w + 화면중앙X;  sy = y2*w + 화면중앙Y;
// 3) 깊이 정렬(화가 알고리즘) — 먼 것부터 그린다
order.sort((a,b) => z[a] - z[b]);
// 4) 깊이 페이드 — 뒤로 갈수록 흐리게
alpha *= 0.12 + w*w*1.05;
```

## 7. ★우선순위 3 — 이것부터 하면 된다

### 1순위. 백본 필터 (약 10~25줄) — **먼저 이걸 안 하면 나머지가 다 무의미하다**
**왜 1순위인가:** 운영자가 화면에서 본 털뭉치의 원인은 그리는 *방법*이 아니라 그리는 *양*이다. 개념당 공기 다리가 중앙값 193개인데(관계는 3개, 64배) 이걸 다 그려놓고 어떤 기법을 얹어도 털뭉치는 그대로다. 그리고 이 하나가 **다른 모든 기법의 비용을 같이 낮춘다.**
- 실행: 노드당 상위 k 슬라이더(기본 **k=5, 1,186간선**). 여유 되면 디스패리티 필터로 승급
- **삭제 아님.** 슬라이더를 끝까지 밀면 21,869개 전량이 그대로 나온다. 헌법 위반 아님

### 2순위. 가산합성 (약 1~5줄) — **운영자가 본 그 그림이 여기서 나온다**
**왜 2순위인가:** 1순위로 양을 줄인 다음에 켜야 발광이 산다. 순서를 바꾸면 화면이 하얗게 포화될 뿐이다(실측: 밝기 255).
- 실행: 공기 층을 `lighter` + 아주 낮은 알파(0.002~0.02)로. **굵기는 오히려 1px로 줄이고 밝기로 말하게 한다**
- ⚠**번들링과 동시에 켜지 마라** (실측 ×11)
- 보너스: 지금 화면의 "계층 ×0.50 · 지구본 ×0.28" 하드코딩 보정(1249행)이 필요 없어진다. 가산합성은 밀도가 스스로 밝기를 정하므로

### 3순위. 3D 힘 배치에 z축 추가 (약 15줄) — **가장 싸게 "뉴런처럼" 보이게 한다**
**왜 3순위인가:** 원근·회전·깊이 페이드가 **이미 구현돼 있다.** 지금 지구본 모드는 노드를 구 껍질에 고르게 뿌리는데, 그래서 모든 간선이 구를 가로지르는 현이 되어 가운데가 뿌옇다(이전 작성자가 1243~1248행에 직접 적어둔 문제다). 힘 배치를 z까지 확장하면 **뭉칠 것은 뭉치고 빌 것은 비는 진짜 3차원 덩어리**가 된다. 비용은 프레임 예산의 3%.
- 실행: 기존 뉴런 모드 힘 계산에 `Z[]` 하나 추가 → 기존 투영 파이프라인에 그대로 물림
- ⚠**공기 간선을 인력에 넣지 마라.** 밀도 70.8%라 전부 한 덩어리가 된다. 인력은 계층 300 + 관계(현재 828)만

**이 3개 합계 ≈ 30~45줄. 이걸로 운영자 이미지 1번의 핵심(밀도 발광 + 3차원 덩어리)에 도달한다.**
번들링(#6)·층 배치(#7)는 그다음, 그것도 "1·2순위를 하고도 여전히 안 읽힐 때"만.

## 8. 내가 틀렸을 수 있는 지점 (자기 반증)

1. **★절대 시간 숫자가 도령님 화면과 다를 수 있다.** 내 측정 창은 `hidden`이라 GPU 2D 가속이 꺼진 상태였다(GTX 1080이 꽂혀 있는데도). **도령님이 실제로 창을 띄웠을 때의 fps는 `[미측정]`이다.** GPU가 붙으면 전부 훨씬 빨라져서 "백본 없이도 그냥 되네?"일 수 있다. → **그래도 1순위는 안 바뀐다.** 백본 필터의 근거는 성능이 아니라 **"공기 다리 193개는 정보가 아니다"(§3-4)**이기 때문이다. 성능은 덤이다.
   **누군가 도령님 브라우저에서 실제 fps를 재봐야 한다. 이건 내가 못 한 숙제다.**
2. **가산합성이 도령님 눈에 예쁠지는 내가 모른다.** 나는 "밝기가 밀도에 비례한다"를 수치로 증명했을 뿐(58.9 vs 36.3), **그게 보기 좋은지는 안 봤다.** 알파 0.002가 우리 배경·색과 맞는지는 눈으로 맞춰야 한다.
3. **HEB가 직선보다 빠르다는 결과를 나도 못 믿었다.** 같은 간선·같은 순서로 다시 쟀고 재현됐다(380.2 → 235.5). 그래도 이건 **소프트웨어 래스터에서만 참일 수 있다.** GPU에서는 세그먼트 수가 다시 지배할 가능성이 있다 `[추론]`.
4. **내가 한 번 틀렸다가 실측으로 잡았다.** "배칭하면 가산합성이 안 될 것"이라 의심했는데 **틀렸다**(K=0/1/500 밝기 동일). 안 재고 썼으면 "발광을 원하면 배칭을 포기하라"는 **틀린 설계**를 권할 뻔했다. → 이 문서의 다른 추론들도 같은 종류로 틀렸을 수 있다. **`[추론]` 딱지가 붙은 건 전부 재보고 쓰라.**
5. **번들링 적합성 판정이 박할 수 있다.** 나는 중주제쌍 98.8% 포화를 들어 "줄기도 털뭉치"라 했는데, **백본 필터를 먼저 걸면 중주제쌍도 같이 줄어든다.** 그 조합을 나는 안 쟀다 `[미측정]`. 재보면 번들링 순위가 올라갈 수 있다.

## 9. 다른 위원과 갈릴 것 같은 지점

**갈림 1 — "공기를 화면에서 걸러라"가 헌법 위반이라는 반론**
> 예상 반대: *절대 원칙이 "동시출현 21,916개를 삭제하지 마라"이고, 잘라내면 '옆으로 샐' 다리가 0.42%로 죽어 보드 1-19④가 죽는다.*
> **내 답: 나는 삭제를 제안한 적이 없다.** 데이터·조회·전파는 전량 그대로다. 내가 줄이자는 것은 **한 프레임에 화면에 칠하는 선의 수**뿐이고, 슬라이더를 끝까지 밀면 전량이 나온다. 그리고 **지금 화면도 이미 공기 층이 기본 꺼짐(0/21,869)이다** `[실측]` — 즉 이 논쟁은 이미 결론이 나 있고 나는 "0 아니면 전량" 대신 **중간 눈금을 두자**고 말하는 것이다.

**갈림 2 — "번들링부터 하자"는 위원과**
> 예상 반대: *운영자가 원한 건 줄기로 묶인 그림이고, 계층이 있으니 번들링이 정답이다.*
> **내 답: 순서만 다르다.** 나도 번들링에 반대하지 않는다(오히려 실측으로 "직선보다 싸다"는 우군 증거를 냈다). 다만 **백본 없이 번들링하면 1,310가닥짜리 털뭉치가 된다**(§3-3, 실측). 그리고 **번들링 + 가산합성은 ×11로 터진다**(실측). 둘 다 원하면 순서가 강제된다: **백본 → 가산 → (그래도 안 읽히면) 번들.**

**갈림 3 — "그럼 앤트로픽 그림은 참고할 게 없다는 거냐"**
> **내 답: 아니다. 그림은 여전히 정답에 가깝다.** 다만 그 그림이 **앤트로픽 것이 아니고, 옵시디언 기본 그래프 뷰이며, "실시간 신경망"이 아니라는 것**이 확인됐을 뿐이다. 우리가 베낄 것은 출처가 아니라 기법이고, 그 기법은 전부 공개돼 있어 오히려 더 낫다. **다만 이 화면을 두고 "앤트로픽처럼"이라고 부르는 건 그만두자. 사실이 아니고, 이 프로젝트는 사실이 아닌 걸 이름에 넣지 않는다.**

**갈림 4 — 숫자가 서로 다를 것이다**
> 다른 위원의 관계 간선 수와 내 것이 다를 수 있다. **틀린 게 아니라 시각이 다르다.** 실측: 587(소집장) → 627(23:12) → 828(23:22). `relation_edges.jsonl`이 30분 사이 두 번 커졌다. **의장께: 이번 회차 숫자는 전부 시각을 붙여 대조해야 한다.** 시각 없는 수치 대조는 또 한 번의 "틀린 인계 수치"를 만든다.

## 10. 하지 말아야 할 것 (내 관점의 금지 목록)

1. **three.js·d3·cytoscape·3d-force-graph를 쓰지 마라.** 제약 위반이고, **필요도 없다** — 위 7개 기법 중 외부 의존이 필요한 게 하나도 없다.
2. **번들링과 가산합성을 동시에 켜지 마라.** 실측 ×11(308ms → 3,447ms). 에러가 안 나고 그냥 느려지므로 **이 프로젝트가 100% 겪은 "조용한 오작동"의 교과서적 형태다.**
3. **캔버스 컨텍스트에 `willReadFrequently:true`를 넣지 마라.** GPU 백엔드가 통째로 꺼진다(실측 2ms → 357ms, 175배). 디버깅용으로 켰다가 지우는 걸 잊으면 화면이 조용히 죽는다.
4. **공기 간선을 힘 배치의 인력에 넣지 마라.** 밀도 70.8%라 249개가 한 덩어리로 뭉쳐 배치가 무의미해진다 `[추론]`.
5. **가산합성을 필터 없이 전량에 켜지 마라.** 화면 중앙 밝기가 255로 포화한다(실측). 발광이 아니라 백지다.
6. **Barnes-Hut 옥트리를 넣지 마라.** 316노드에 300줄 추가하고 얻는 게 없다.
7. **화면에 손잡이를 더 늘리지 마라.** 이미 35개 이상이다. 새 기능은 **기본값으로 들어가야지 토글로 들어가면 안 된다.**
8. **"앤트로픽 유출 그래프처럼"이라는 표현을 문서·코드 주석에 쓰지 마라.** 오보로 판정된 건이다(커뮤니티 노트). 우리가 근거 없는 걸 이름에 박는 순간 이 프로젝트의 원칙이 무너진다.
9. **내 ms 숫자를 도령님 화면의 fps로 옮겨 적지 마라.** 내 측정은 GPU가 꺼진 최악 조건이다. **배수만 인용하고, 절대 fps는 도령님 브라우저에서 다시 재라.**
