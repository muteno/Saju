## 1. 한 줄 결론

## 3. 다섯 질문에 대한 답

### 3-1. 합칠 것인가, 입구 하나인가, 지금이 맞나 → **입구 하나 + 화면은 역할별 유지 + 전 화면에 같은 네비와 판 도장**

- **"하나로 합치기" 반대.** 근거: ①합본은 7.0MB짜리 단일 파일이 되고 그중 82%가 개념트리다 [실측] — 매일 아침 여는 문이 제일 무거운 화면에 인질 잡힌다. ②다섯 화면은 답하는 질문이 다르다(현황판=공정 어디까지 / 개념지도=사전·책갈피 / 지식망=연결 구조 / 뉴런망=표 정렬·검색 / 개념트리=계층 근거 열람). 질문이 다른 걸 한 페이지에 붙이면 스크롤 지옥이지 통합이 아니다. ③자립형 헌법(§5)은 화면별 독립 파일일 때 가장 지키기 쉽다.
- **"지금이 맞다"도 반대.** 근거: 섬 2개 [실측 2-3], 문의 거짓말 3건 [실측 2-2], 세 시대 공존 [실측 2-1]. 지금 구조는 "5개를 다 열고, 어느 게 최신인지 사람이 맞혀야 하는" 구조다.
- **채택안 = 문 하나.** 이미 타 담당이 만드는 파이프라인.py+허브가 뼈대다. 내가 UX에서 얹는 것 3가지:
  1. **문은 HTML이 아니라 bat 더블클릭이다.** 순서: 더블클릭 → 파이프라인(낡은 단계만 재실행, 수 초~수십 초) → 허브 열림. 정적 HTML은 자기가 낡았는지 스스로 모른다. **문에서 갱신이 일어나야 허브가 항상 방금 찍은 사진이 된다.** 운영자는 이미 "현황판_갱신.bat 더블클릭"이 습관이다(CLAUDE.md에 그렇게 안내돼 있음) — 새 습관을 가르칠 필요가 없다.
  2. **허브 맨 위는 파이프라인 표가 아니라 "오늘 뭐가 달라졌나"다.** 현재 파이프라인.py의 허브 설계는 단계 상태표가 중심인데 그건 방자(세션)용 정보다. 도령님용 첫 화면은 3-5절의 델타 칩이 위, 상태표는 아래.
  3. **다섯 화면 전부에 같은 네비 5버튼 + 같은 판 도장**(3-4). 지식망에만 있는 네비(22:55 신설)를 전 화면에 복제하면 섬이 사라진다. 수정량은 빌더 4곳에 몇 줄씩이다.
- **중기 수렴(삭제 아님):** 지식망이 이미 트리 모드를 갖고 개념트리·뉴런망의 데이터를 읽는 배선이 과제로 잡혀 있으므로, **흡수가 실측으로 증명되면**(지식망 안에서 표 정렬·계층 근거 열람이 다 되면) 허브에서 두 화면을 "자세히" 줄로 내린다. **파일은 남긴다. 되돌림 = 허브 링크 한 줄 복원.** (규칙 5 준수: 대체물과 복귀 경로 명시)

### 3-2. 처음 3초에 무엇을 봐야 하나

**지금 보이는 것 [실측]:**
- 현황판: 제목 + 회색 작은 글씨 "갱신 08:32" + **거짓 진행률 0% 막대**. 최악의 3초다 — 첫눈에 들어오는 유일한 큰 신호가 틀린 숫자다.
- 개념지도: 제목 + 갱신 22:53 + 검색창 + 과목 15개 네비. 자기 역할(사전)에는 맞는 3초.
- 뉴런망: 제목 + 카드 5개(개념 249·다리 21,869·평균 176·100+ 214·외딴 0) + "읽는 법" 안내. 양호.
- 개념트리: 5.7MB 로딩 [시간 미측정] 후 규칙 설명 문단. 갱신 09:08이 낡았다는 표시는 없음.
- 지식망: 어두운 캔버스에 그래프 + 좌우 패널 + 상단 스탬프. 기본 레이어가 1·2층이라 털뭉치는 걷혔으나, **뭘 보라는 것인지는 안 알려준다.**

**있어야 하는 3초 (허브 기준) — "신선도 1 · 변화 3 · 행동 1":**
1. **신선도 등 1개** — "방금 그림 (23:07, 제N판)" 초록 / 낡으면 노랑·빨강. 크게.
2. **변화 칩 최대 3개** — "+문단 0 · 관계다리 587(±0) · 도달불가 59→52" 식. **반드시 품질 숫자 동반**(예: "인용 불일치 0 유지") — 이 프로젝트 사고는 전부 '통과하면서 틀림'이었으므로 양만 보여주면 위험하다.
3. **행동 1개** — "도령님 결정 대기 N건" 중 최상위 1건만. (지금 현황판은 결정 대기 4건이 표 안에 묻혀 있다.)
- 숫자는 첫 화면에 **5개 초과 금지.** 지금 현황판 첫 스크롤엔 큰 숫자가 11개 있다(공정 6 + 창고 5) [실측]. 다 보여주는 것은 아무것도 안 보여주는 것이다.
- **모순 배지**: 빌드 시점에 자기 데이터 안 모순을 검사해 화면에 박는다. 예: 커버리지 done=0인데 창고 문단>0이면 그 카드에 "⚠이 숫자는 서로 안 맞음 — 집계 결함 의심"을 자동 표기. 조용한 오작동 100% 프로젝트에서는 **화면이 스스로 자수하는 것**이 합격 표시보다 중요하다.

### 3-3. 6축을 한 화면에 동시에 — **정적으로 전부는 못 읽는다. 축마다 채널을 배정하고, 위치를 두고 다투는 두 축은 모드로 시분할한다**

사람 눈이 한 번에 전주의적으로 읽는 시각 채널은 3~4개가 한계다 [추론 — 시각화 일반 원칙. 이 운영자 대상 실험은 미측정]. 화면이 가진 채널은 위치·크기·굵기·색상·진하기·발광 정도인데, 6축을 전부 정적으로 칠하면 무지개 스파게티가 된다. 배정안:

| 운영자 축 | 채널 | 상태 [실측 기준] |
|---|---|---|
| ① 계층 | **위치(레이아웃)** — 트리 모드 | 지식망 트리 모드 + 1층 간선 315. 있음 |
| ② 연결 강도 | **선 굵기** | 있음 (weight 12종) |
| ③ 붙은 지식 | **노드 크기** (문단 수) | 데이터 있음(metrics 문단 필드) — 크기 배선 확인 필요 |
| ④ 거리 | **위치** — 뉴런(힘) 모드 | ①과 위치를 두고 다툼 → **모드 전환으로 시분할** (이미 4모드 있음). 단 거리의 근거 그래프는 관계층(밀도 1.9%)이어야 함 — 공기층(70.8%)은 평균거리 1.29라 "가깝다"가 정보를 안 나름 [밀도 실측 계산 · 거리는 소집장 인용] |
| ⑤ 빛의 강도 | **발광 — 정적 속성이 아니라 상태 채널로 예약** | 미착수. 아래 3-5와 배선: **"지난 판 대비 달라진 노드·간선만 빛난다"** |
| ⑥ 신뢰도 | **진하기 + 호버 상세 + 필터 슬라이더** | 진하기=저자 확신도로 이미 사용. 단 결정론/축자/가설이 한 축에 섞이면 안 됨 → 색이 아니라 **필터**("신뢰 0.7 미만 흐리게")로 |

- **기본 화면 = ①위치 + ②굵기 + ③크기 세 축만.** ④는 모드 버튼, ⑥은 호버·필터, ⑤는 "오늘 변화" 토글. 이러면 여섯 축이 **한 화면 안에서** 전부 접근 가능하되, 한 순간에 눈이 읽는 건 3개다.
- ④⑤⑥이 같은 축이냐는 쟁점에 대한 UX 답: **다른 축이다. 겹치면 채널을 뺏는다.** ②강도(근거가 얼마나 강한가)와 ⑥신뢰(그 근거를 얼마나 믿나)는 데이터 축이고, ⑤빛은 **시간 축**(지금 무엇이 활동했나)일 때만 화면에서 살아남는다. 셋을 다 선 굵기·색에 욱여넣으면 서로를 지운다.
- 운영자 원문 "동시에"의 해석: 여섯 물감을 한 그림에 다 칠하는 게 아니라 **화면을 떠나지 않고 여섯 축을 오갈 수 있으면 충족**이라고 본다. 이건 지시의 재해석이므로 갈릴 수 있다(§5).

### 3-4. "낡음"을 화면이 어떻게 말해야 하나 — **낡음은 세 종류고, 처방이 다 다르다**

| 층위 | 실물 [실측] | 처방 |
|---|---|---|
| (a) 화면이 데이터보다 낡음 | 현황판 08:32 vs data 22:54 | 파이프라인의 mtime 비교(이미 설계됨) + **문에서 자동 재생성** — 운영자가 볼 일 자체를 없앤다 |
| (b) 화면끼리 세대 불일치 | 22:53/22:54/22:55 — 같은 세대인가? 사람이 모름 | **판(세대) 도장**: 파이프라인 1회 실행 = 도장 1개("제47판 · 07-25 23:07"). 전 화면 상단에 동일 표기. 판 번호가 다르면 눈으로 보인다. 시각 2개 비교는 사람 몫이지만 판 번호 비교는 한눈이다 |
| (c) 시각은 최신인데 내용이 낡음 | 하드코딩 할 일 "도화도레 191편"(완결된 일) [실측 192행] | 시각·판 도장으로 **못 잡는다.** 손글씨 목록을 빌더 밖 데이터 파일로 빼고, 화면엔 "이 칸은 사람이 손으로 적음 · 마지막 수정 MM-DD" 라벨을 강제 |

여기에 하나 더 — **(d) 자기 나이 배지.** 정적 HTML도 이것은 할 수 있다: 생성 시각을 구워 넣고 JS `Date.now()`와 비교해 "이 화면은 **N시간 전 사진**"을 상단에 표시, 24시간 넘으면 노랑, 사흘 넘으면 빨강 + "현황판_갱신.bat 더블클릭이면 새로 그려져요" 한 줄. 네트워크 0·서버 0·자립형 유지. 운영자가 즐겨찾기로 화면을 직접 열어도(문을 우회해도) 낡음이 자수한다. **원칙: 낡음은 죄가 아니다. 낡음을 숨기는 게 죄다. 낡은 화면도 자기가 낡았다고 말하면 자산이다.**

### 3-5. 매일 여는 사람에게 — **지겨움의 반대는 화려함이 아니라 "내 어제와 비교됨"이다**

1. **판마다 스냅샷 1행 자동 보관** (history.jsonl append — 날짜·문단·다리·도달불가·유닛 수·게이트 통과 수치). 전례 있음: `_before_전사반입.csv`로 전/후 비교를 이미 해봤다 [실측 존재]. 그걸 1회성에서 상시로 승격.
2. **허브 맨 위 "오늘의 변화" 칩 3개** (3-2의 그 칩). 변화가 없으면 "오늘은 그대로"도 정보다 — 매일 같은 숫자를 다시 읽게 하는 게 지겨움의 정체다.
3. **"오늘의 한 줄" 자동 문장 1개.** 규칙 기반으로 충분(LLM 불요): 가장 큰 변화 축을 골라 "재물·돈에 첫 결정론 다리가 놓였다 — 도달불가 59개 중 하나가 줄었다" / "석우당 전사가 절반을 넘었다(808→N/1,901)". 도달불가 59개 목록(재물·직업·관계…)이 줄어드는 것이 이 프로젝트의 진짜 진도이므로, **이 한 줄의 단골 소재는 "사람이 실제로 묻는 것에 다리가 생겼는가"다.**
4. **⑤빛의 강도를 여기 배선**: 지식망에 "이번 판에서 달라진 것만 빛나기" 토글. 매일 열 때마다 어제와 다른 노드가 빛나므로 그림이 매일 다르다. 뉴런 은유와도 맞다 — 최근 발화한 시냅스가 빛난다. 운영자가 이름 붙인 축에 실제 쓸모를 주는 배선이다.
5. **결정 대기 1자리 고정** — "도령님 결정 기다리는 것 N건". 운영자만 할 수 있는 일이 항상 문 앞에 있으면, 매일 여는 이유가 생긴다. (지금 현황판의 결정 대기 4건은 표 안에 묻혀 있고 그마저 낡았다.)

## 4. 내가 틀렸을 수 있는 지점 (자기 반증)

1. **"문 = bat" 전제는 운영자 습관을 재지 않은 채다 [미측정].** 운영자가 html을 즐겨찾기로 직접 열어왔다면 문 개선의 효과가 깎인다. 그래서 (d) 자기 나이 배지를 이중 안전으로 넣었지만, 습관 실측(운영자에게 한 줄 질문이면 됨) 전에는 배치 우선순위를 확신할 수 없다.
2. **델타 강조는 처리량 숭배를 부를 수 있다.** 이 프로젝트 사고는 100% 조용한 오작동이었다 — "+문단 900"은 품질 신호가 아니다. 내 처방(품질 게이트 동반 표기)이 지켜지지 않으면, 내 제안은 보드 1-18("유의미하게")을 화면 차원에서 배반하는 도구가 된다.
3. **6축 답(기본 3축+시분할)은 시각화 일반론에서 온 추론이다.** 이 운영자를 대상으로 실험하지 않았다 [미측정]. 운영자가 "동시에"를 문자 그대로(한 그림에 6축 정적) 원한다면 내 답은 지시 불이행이 아니라 지시 재해석이므로, 의장이 운영자 원문으로 판정해야 한다.
4. **나는 브라우저로 실제 열지 않고 파일 구조로 판단했다.** 개념트리 로딩 시간, 지식망 초기 렌더의 실제 인상(줌 레벨·라벨 겹침)은 코드에서 추론한 것이다 [미측정]. "첫 3초" 서술 중 지식망·개념트리 항목은 실행 검증이 남아 있다.

## 5. 다른 위원과 갈릴 것 같은 지점

1. **"파이프라인.py가 이미 허브를 만드니 UX 의견은 중복"이라는 반론(엔진 담당 예상).** 답: 중복이 아니라 순서 문제다. 현재 설계된 허브는 단계 상태표가 중심 — 그건 방자용이다. 도령님의 3초는 델타가 위, 상태표가 아래여야 한다. 코드로는 블록 순서 바꾸기지만, 매일 아침의 첫 인상을 결정한다.
2. **"5개를 진짜 한 화면으로 합치자"는 위원과.** 답: 7.0MB 중 82%가 개념트리다 [실측]. 합본은 문을 제일 무거운 화면에 인질 잡히고, 자립형 원칙의 수정 단위도 무너진다. 합치기의 이득(이동 클릭 1회 절약)은 전 화면 공통 네비로 동일하게 얻는다.
3. **"뉴런망(표)·개념트리는 지식망에 흡수됐으니 지우자"는 위원과.** 답: 규칙 5 위반이다. 흡수가 실측으로 증명되기 전까지는 허브에서의 강등(2열 "자세히"로)까지만. 파일 삭제는 반대. 되돌림 = 링크 복원 한 줄.
4. **⑤빛의 해석이 갈릴 수 있다.** "빛 = 조회·사용 빈도(어느 다리를 자주 타는가)"로 읽는 위원이 있을 것이다. 그 해석이 최종형으로는 더 맞다 — 단 조회 로그는 앱이 생겨야 존재한다. 지금 배선 가능한 유일한 빛은 "변화"뿐이고, 나중에 조회 로그가 생기면 같은 채널에 승격하면 된다(호환됨). 지금 정의를 비워두면 ⑤는 계속 ⬜미착수로 남는다.
5. **"낡음 배지가 시끄럽다, 회색으로 작게"라는 미학적 반론.** 답: 이 프로젝트에서 조용함은 미덕이 아니라 사고 이력이다. 낡음·모순 표시는 크고 시끄럽게가 기본값이어야 한다.

## 6. 하지 말아야 할 것 (F1 관점 금지 목록)

1. **화면을 서버 필요 구조로 만들지 마라** (로컬 http 서버·CDN·외부 폰트·fetch) — 자립형 헌법(§5) 위반. 낡음 표시도 반드시 "구운 시각 + 로컬 시계"로만.
2. **개념트리 5.7MB를 허브나 다른 화면에 인라인 병합하지 마라** — 문이 무거워지는 순간 매일 열기가 죽는다.
3. **갱신 시각만 찍고 판(세대) 번호 없이 두지 마라** — 시각 두 개의 비교는 사람 몫이 되고, 그 사람은 비전문가다.
4. **손글씨 목록(할 일·안내 문구)을 빌더 py 안에 계속 하드코딩하지 마라** — "방금 갱신됐는데 내용은 낡은" 화면을 만든다(실물: build_dashboard.py 192행). 데이터 파일로 빼거나 최소한 '손으로 적음 + 수정일' 라벨을 강제하라.
5. **델타 칩에 처리량만 놓지 마라** — 품질 게이트 수치(인용 불일치 0·재현 성공 등) 동반 없는 증가 숫자는 숫자 숭배다.
6. **동시출현 간선을 삭제하지 마라** — 이미 기본 OFF 강등으로 해결돼 있다(§5 헌법 그대로). 화면 정리를 이유로 삭제로 승격하는 순간 보드 1-19④("옆으로 샐 수 있어야 함")가 죽는다.
7. **6축을 한 정적 그림에 전부 인코딩하지 마라** — 무지개 스파게티. 위치를 다투는 축(①④)은 모드로, 시간 축(⑤)은 하이라이트로, 판단 축(⑥)은 필터로.
8. **수치 정의를 화면마다 따로 계산하지 마라** — 다리 수·문단 수 세는 법이 화면마다 다르면 "틀린 인계 수치 8건"이 화면판으로 재발한다. 측정은 knowledge_metrics(계기판) 한 곳, 화면은 그리기만.
9. **"운영자가 알아서 5개를 돌며 비교하겠지"를 전제로 설계하지 마라** — 실측된 현실은 그 반대다: 문이 하나(현황판)로 굳어 있었고, 그 문이 14시간 낡은 채 거짓 0%를 보여주고 있었다.
