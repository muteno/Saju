## 1. 한 줄 결론

**성능은 이 프로젝트의 제약이 아니다. 통합해도 안 무겁다 — 22,899간선을 다 그려도 4.95ms(202fps)이고, 이미 그게 `지식망.html` 553KB 안에 전부 들어 있다.**
진짜 상한은 픽셀도 MB도 아니라 **글자 수(라벨 6,000개)와 레이아웃 박스 수(6,000개)** 두 개다.
그러니 "무거우니까 줄이자"는 말이 나오면 그건 성능 근거가 아니라 **가독성 근거**다 — 이름을 바꿔 부르지 마라. 성능을 핑계로 자르면 그건 조용한 truncation이다.

### 2-2. Q2 — Canvas vs SVG vs WebGL

측정 조건: 캔버스 3000×1724 (5,172,000픽셀). 운영자 실제 캔버스(3000×1812, dpr=2)와 동급이 되도록 강제 리사이즈해서 쟀다.

**① Canvas 2D — 실제 `지식망.html`의 `draw()`를 그대로 호출** [실측]

| 최소 강도 | 공기 간선 | 총 간선 | draw() | fps |
|---|---:|---:|---:|---:|
| 기본(공기 OFF) | 0 | 1,030 | 3.39 ms | 295 |
| w≥100 | 3,276 | 4,306 | 2.92 ms | 343 |
| w≥10 | 10,745 | 11,775 | 3.38 ms | 296 |
| **w≥1 (전량)** | **21,869** | **22,899** | **4.95 ms** | **202** |

**간선을 22배 늘렸는데 시간은 1.46배밖에 안 늘었다.** 왜인지 계측해서 확인했다 — `ctx` 함수를 가로채 호출 횟수를 셌다:

```
공기 전량 ON 시 1프레임:  moveTo 23,563회 · lineTo 24,160회 · 그런데 stroke() 는 1,365회
```

→ 빌더가 **같은 스타일 간선을 한 경로(path)에 몰아 담고 stroke를 한 번만 친다.** 이게 지금 화면이 빠른 이유다. 이 배치 기법을 잃으면 숫자가 달라진다. 그래서 잃었을 때를 따로 쟀다 [실측]:

| 방식 | 21,869간선 | 비고 |
|---|---:|---|
| A. 배치(현재 방식) | **1.13 ms** | stroke 1회 |
| E. 색 6버킷으로 묶기 | 1.22 ms | stroke 6회 |
| F. 색6×굵기6 = 36버킷 | 1.21 ms | stroke 36회 |
| B. 굵기만 간선별로 | 4.00 ms | stroke 21,869회 |
| **C. 색+굵기+투명도 전부 간선별** (축②⑤⑥ 동시) | **4.40 ms** | stroke 21,869회 |
| D. shadowBlur 글로우 | 2,000개 1.25ms → **약 14 ms** 환산 | 🔴 유일하게 비싼 것 |

**축②(굵기·채색)·⑤(빛의 강도)·⑥(신뢰도)를 간선마다 전부 다르게 줘도 4.40ms다. 걱정할 것 없다.**
단 **⑤를 shadowBlur(진짜 광채)로 구현하면 14ms**로 프레임 예산의 84%를 혼자 먹는다 → 강조된 소수(수백 개)에만 걸어라.

**② SVG** [실측] — `<line>` 요소를 실제로 만들어 붙이고 쟀다

| 간선 수 | 생성 | 첫 레이아웃 | 합계 | 줌(그룹 transform) | **전 간선 속성 갱신** |
|---:|---:|---:|---:|---:|---:|
| 1,000 | 7.2 ms | 18.6 ms | 25.8 ms | 0.4 ms | 2.7 ms |
| 5,000 | 25.0 ms | 9.9 ms | 34.9 ms | 0.3 ms | 10.3 ms |
| **22,756** | **128.8 ms** | 53.3 ms | **182.1 ms** | 0.6 ms | **50.8 ms** 🔴 |

SVG의 함정은 첫 렌더(182ms — 한 번이니 참을 만하다)가 아니라 **속성 갱신 50.8ms**다. LOD 전환·최소강도 슬라이더·호버 강조 — 전부 "전 간선 속성 갱신"이다. 그때마다 **20fps로 떨어진다.** 그리고 이건 낙관적 수치다(측정 시 페인트까지는 강제 못 했다).

**③ WebGL2** [실측] — 셰이더·버퍼를 직접 짜서 쟀다(라이브러리 0)

```
GPU: ANGLE (NVIDIA GeForce GTX 1080, Direct3D11)
22,756 선분 draw = 0.005ms 미만 (타이머 해상도 이하로 측정 불가)
```

빠르다. 그런데 **얻는 게 4.95ms → 0.005ms다. 5ms를 아끼자고 치르는 값이 크다:**
- `gl.LINES`는 **굵기 가변이 안 된다**(대부분의 구현에서 lineWidth는 1로 고정). 축②(굵기=강도)를 살리려면 간선 하나를 삼각형 2개로 직접 만들어 정점 버퍼를 손으로 채워야 한다 = 간선당 6정점, 22,756간선 = 136,536정점을 매 레이아웃마다 재생성.
- 텍스트가 없다. 라벨은 결국 Canvas 2D를 겹쳐야 한다 → 두 개를 관리.
- 셰이더 컴파일 실패는 **화면이 까맣게 나오면서 에러가 안 뜬다.** 이 프로젝트의 사고 유형(조용한 오작동) 그 자체다.

**상한 정리** — 60fps(16.7ms) 예산 기준

| 방식 | 실측 근거 | 간선 상한 |
|---|---|---:|
| Canvas 2D 배치 | 21,869=1.13ms | **약 30만** [추론] |
| Canvas 2D 간선별 스타일 | 21,869=4.40ms | **약 8만** [추론] |
| Canvas 2D + 글로우 | 21,869≈14ms | **약 2만 5천** [추론] |
| SVG | 갱신 22,756=50.8ms | **약 5,000** (실사용) |
| WebGL | 22,756<0.005ms | 100만+ [추론] |

**→ 판정: Canvas 2D. 이미 쓰고 있고, 필요량 22,899에 대해 여유가 3.4배(간선별 스타일 기준) 있다. 바꿀 이유가 없다.**

**인터랙션(호버·클릭·줌)까지 되려면?** [실측] — 걸리지 않는다.

```
노드 328개 최근접 탐색      = 0.002 ms   (60fps 예산의 0.01%)
간선 22,756개 무차별 탐색   = 0.41  ms   (60fps 예산의 2.5%)
recomputeVis() 전체 재계산  = 0.63  ms
physics() 1스텝             = 0.07  ms
```

공간 인덱스(쿼드트리) 같은 것 필요 없다. **무차별 반복(brute force)으로 충분하다.** 22,756개를 매 마우스 이동마다 다 훑어도 0.41ms다.

### 2-3. ★진짜 상한은 간선이 아니라 글자다 [실측]

이게 이번 측정에서 가장 중요한 발견이다.

| 캔버스에 그리는 것 | 개수 | 시간 |
|---|---:|---:|
| 간선 전량(배치) | 22,899 | **4.95 ms** |
| 노드 원 | 328 | 0.08 ms |
| 노드 원 | 5,000 | 0.56 ms |
| 라벨(한글 12px) | 328 | 0.29 ms |
| 라벨 | 1,000 | 0.61 ms |
| 라벨 | 5,000 | 2.42 ms |
| **라벨** | **22,756** | **38.33 ms** 🔴 |
| measureText(겹침 회피용 측정) | 22,756 | 6.7 ms |

**간선 22,899개(4.95ms)보다 라벨 22,756개(38.33ms)가 7.7배 비싸다.**

→ **60fps 라벨 상한 = 약 6,000개.** (16.7 − 4.95(간선) − 0.6(노드) ≈ 11ms ÷ 0.00168ms/라벨 ≈ 6,500)
→ 안전선 = **2,000개**.

통합 화면 설계에서 접어야 할 것은 간선이 아니라 **글자**다. 지금까지 논의가 "간선 22,756개를 어떻게 줄이나"에 쏠려 있었다면 방향이 틀렸다.

### 2-4. Q3 — `개념트리.html` 5.7MB는 실제로 열리나

**판정: 열린다. 그런데 "닫혀 있어서 열린다."** [실측 — 실제로 브라우저에 띄워서 쟀다]

파일 구조부터 정독했다:

```
개념트리.html  5,740,232 B · 261줄 · 3,691,177자
  <script>  0개      ← 자바스크립트가 한 줄도 없다
  <canvas>  0개
  <svg>     0개
  <div>     32,237
  <span>    12,536
  <a>       50,278       ← '공유 가지' 표의 상호참조 링크
  <details> 2,679   그중 열린 것(open) 0개
  전체 태그 208,468
```

**순수 정적 HTML이다.** 리프트 기반 계층을 `<details>`로 미리 다 펼쳐 박아 넣은 것. 그래서 5.7MB다.

열어본 결과:

```
다운로드          42 ms
domInteractive   314 ms
load             337 ms      ← 0.34초. 전혀 안 무겁다
요소 수      105,463개
JS 힙            1.2 MB      (JS가 없으니 당연)
닫힌 상태 스크롤 높이  15,943 px
전체 리플로우     13.9 ms     ✅
```

**왜 105,463개나 되는데 리플로우가 13.9ms인가 —** 닫힌 `<details>` 안의 내용은 브라우저가 **레이아웃하지 않기 때문**이다. 실제로 레이아웃되는 박스는 2,679개(요약줄)뿐이다. 이게 유일한 방어선이다.

그 방어선이 무너지는 순간을 쟀다:

```
2,679개 전량 펼치기   → 1,926.8 ms 정지 (1.9초 프리즈)
                       스크롤 높이 15,943 px → 1,391,843 px (87배, 화면 1,500개 분량)
다시 접기             →   231.9 ms
스크롤 20스텝(강제 레이아웃 동반) → 898.7 ms = 스텝당 45ms = 22fps
```

그리고 같은 크기대에서 **박스가 처음부터 보이면** 어떻게 되는지 대조군으로 확인했다(위 2-1 표): 13,000박스 = 1,519ms, 38,072박스 = 3,226ms, 전량 펼치기 시도 = **30초 초과 후 렌더러 크래시**(탭이 실제로 죽었다).

**결론 3줄:**
1. 지금은 안전하다 — 0.34초에 열리고 리플로우 13.9ms다. "5.7MB라 무겁다"는 걱정은 틀렸다.
2. 안전한 이유가 **접혀 있기 때문**이라서 안전 마진이 없다. "전부 펼치기" 버튼 하나, 또는 브라우저 Ctrl+F가 자동으로 details를 펼치는 동작 하나면 1.9초 프리즈로 간다.
3. 통합 화면에 **DOM인 채로 합치면 안 된다.** 합치는 순간 그 문서의 모든 리플로우가 105,463요소 비용을 낸다.

부수 발견: 닫힌 상태에서 `document.body.innerText`가 **9,775자**뿐이다(파일은 369만 자). 즉 화면에 보이는 텍스트는 0.26%다. 운영자가 브라우저 검색으로 내용을 찾는 게 사실상 안 된다 [실측]. 이것도 조용한 손실이다 — 자료는 파일에 있는데 사람이 못 찾는다.

### 2-5. Q4 — 인라인이냐, 별도 jsonl + fetch냐

**`file://`에서 fetch가 막힌다는 전제부터 직접 확인했다.** 그리고 결과가 미묘하다 — 그래서 정직하게 셋으로 나눈다.

**[실측] Claude 내장 브라우저(Chromium 148)에서는 동기 XHR이 성공했다.**
실제 `지식망.html`이 `file://`로 열려 있던 탭에서 `data/neuron_edges.jsonl`을 읽었다 → `status=200, length=1,890,951`.

이게 진짜인지 검산했다:
```
파일 크기                       2,180,895 B
LF로 정규화한 문자수            1,869,082 자
CRLF 개행 수                       21,869 개   (= 간선 수와 같다)
1,869,082 + 21,869            = 1,890,951 자
XHR이 보고한 길이             = 1,890,951 자   ★완전 일치
```
→ **정말로 그 파일을 읽었다.** 우연이 아니다.

**[실측] 그러나 같은 브라우저에서 `file:///C:/Windows/win.ini`는 NetworkError로 실패했다.**

이 조합이 결정적이다:
- 표준 Chromium(플래그 없음) = **같은 폴더도 전부 차단**
- `--allow-file-access-from-files` 준 Chromium = **win.ini까지 열린다**
- 여기 = **같은 폴더는 되고 win.ini는 안 된다** → 둘 다 아니다

→ **Claude 브라우저의 자체 폴더 한정 정책이다. 운영자의 Chrome/Edge에 일반화할 수 없다.**

**[미측정] 운영자의 실제 브라우저에서의 동작.** 프리뷰 도구가 `file://`을 띄우지 못해(“files outside the project folder render as static snapshots” 후 탭 종료) 확인하지 못했다. 표준 Chromium 동작에 비추면 **차단이 맞다** [추론].

**→ 결론: fetch/XHR은 못 쓴다고 보고 설계해야 한다.** 대안은 셋이다.

| 방안 | 자립형 유지 | 확실성 | 비고 |
|---|---|---|---|
| **(a) 인라인 (현행)** | ✅ 완전 | ✅ 실측 | 12.31MB까지 0.32초 확인. **20MB까지 여유** |
| (b) `<script src="data.js">` 형제 파일 | ⚠ 파일 2개 | [추론·미측정] | 고전 스크립트는 CORS 프리플라이트 대상이 아니라 `file://`에서 로드된다. 단 **HTML만 옮기면 죽는다** — 메일 첨부·복사 시 조용히 빈 화면 |
| (c) 드래그&드롭 / `<input type=file>` | ⚠ 손이 간다 | ✅ [추론] | `file://`에서도 확실히 동작. 그러나 "더블클릭이면 끝"이 깨진다 |

**권고: (a) 인라인 유지.** 실측상 20MB까지 여유가 있고, "외부 참조 0 · 더블클릭" 헌법을 100% 지키는 유일한 방법이다. (b)는 데이터가 **50MB를 넘어갈 때** 꺼낼 카드이지 지금 꺼낼 카드가 아니다.

**단, 인라인에도 값이 있다 — OneDrive다** [실측]

```
_현황판\ 전체        파일 32개 · 27.4 MB
화면 5개 합           6.99 MB   ← 파이프라인 돌 때마다 전량 재작성 = 전량 재업로드
HTML 5개 속성        전부 ReparsePoint (OneDrive 클라우드 자리표시자)
attrib 플래그        A 만 있음 — O(온라인전용) 없음 · P(고정) 없음
```

지금은 로컬에 실체가 있다(그래서 열린다). 그런데 **P(항상 이 장치에 유지)가 안 걸려 있다.** OneDrive는 저장공간이 빠듯해지면 큰 파일부터 탈수화(dehydrate)한다 → 그러면 **개념트리 5.7MB를 더블클릭할 때 네트워크가 필요해진다.** 헌법의 "오프라인 더블클릭으로 열려야 한다"가 조용히 깨지는 경로다.

→ 조치 1줄: `_현황판\` 폴더에 **"항상 이 장치에 유지"를 걸어라.** 코드 변경 0, 비용 0.

### 2-6. Q5 — 점진적 렌더링·LOD 제안

**설계 원칙: 접는 기준을 간선 수로 잡지 마라. 실측상 간선은 안 비싸다(4.95ms). 글자와 DOM 박스로 잡아라.**

세 예산을 못 박고, 각 구간이 그 안에 들어오게 짠다.

```
예산 A — 캔버스 프레임:  16.7 ms   (간선 5 + 노드 1 + 라벨 11)
예산 B — 라벨:            2,000개 안전 · 6,000개 상한
예산 C — DOM 박스:        2,000개 안전 · 6,000개 상한   (사이드패널·근거 목록)
```

| 줌 | 노드 | 라벨 | 간선 | 접는 것 | 예상 |
|---|---|---:|---|---|---:|
| **L0 전체** (`cam.k < 0.3`) | 대주제 15 + 중주제 51 = **66**만 | **66** | 계층 315 + 관계 587 + 공기 상위 1,500 | 개념 249 라벨 · 공기 20,369 | ~3.5 ms |
| **L1 주제** (`0.3 ≤ k < 1.0`) | 328 전량 | 화면 안 + 겹침 회피 후 **≤300** | 계층 315 + 관계 587 + 공기 w≥10 (10,745) | 화면 밖 라벨 · 공기 11,124 | ~5 ms |
| **L2 근접** (`k ≥ 1.0`) | 화면 안 전량 | 화면 안 전량 (**≤2,000**) + 간선 종류 라벨 | **공기 전량 21,869** + 나머지 전량 | 화면 밖 전부 | ~8 ms |
| **L3 선택** (노드 클릭) | 이웃만 강조 | 이웃 라벨 | 이웃 간선에만 **글로우**(≤500개, ~0.3ms) | — | ~9 ms |

**점진적 렌더링(첫 화면 빨리 띄우기)**은 필요 없다 — 실측 `지식망.html` domInteractive가 **47 ms**다(운영자 실제 파일, `file://`, OneDrive 경로). 47ms를 쪼갤 이유가 없다. 개념트리를 통합할 때만 필요해지는데, 그때는 아래.

**개념트리를 통합할 때만 필요한 2가지**
1. **가상 스크롤** — 보이는 것만 DOM에 만든다. 화면 높이 900px ÷ 행 높이 30px ≈ 30행 + 여유 = **DOM 박스 100개 내외**로 유지. 예산 C의 6,000에 한참 못 미친다.
2. **근거 축자는 클릭할 때만 붙인다** — 지금은 2,679개 details 안에 미리 다 박아뒀다(그래서 5.7MB). 데이터로 들고 있다가 펼칠 때 만들면 DOM 박스가 105,463 → 100대로 떨어진다.

되돌리기: 빌더(`build_concept_tree.py`)는 그대로 두고 출력만 바꾼다. 렌더러 교체이지 자산 폐기가 아니다.

### 2-7. Q6 — 조용한 truncation을 어떻게 강제하나

**지금 상태부터: 이미 반쯤 구현돼 있다** [실측 — `build_graph_view.py` 1042~1056행]

```js
/* ★조용한 truncation 금지 — "N개 중 M개만 표시 중"을 화면에 항상 적는다. */
function counts() {
  function set(id, shown, total, extra) {
    el.textContent = shown.toLocaleString() + ' / ' + total.toLocaleString() + ...;
    el.style.color = (shown < total) ? '#c9a04d' : '#6f7787';   // 모자라면 색이 바뀐다
  }
  set('c_hi', hiShown.length, E_HI.length);
  set('c_re', reShown.length, E_RE.length);
  set('c_co', coShown.length, E_CO.length);
  ...
}
```

좋다. 그런데 **이 방식은 사람이 그 자리에 카운터를 손으로 넣어줘야 작동한다.** 새 레이어를 추가하면서 `set(...)` 한 줄을 빠뜨리면 그 레이어는 조용히 사라진다. 지금 이 프로젝트가 겪은 사고 유형 그대로다.

그리고 실제로 지금 **기본 화면은 간선의 95.5%를 안 그리고 있다** [실측]:

```
기본 상태 (S.showCo = false, 공기 레이어 OFF)
  그리는 것:  계층 315 + 관계 587 + 유닛 92 + 유닛계층 36 = 1,030
  전체:       22,899
  →  4.5%

공기를 켜도 기본 임계 defw = 224 이므로
  그리는 것:  1,030 + 공기 1,501 = 2,531 / 22,899 = 11.1%
  숨는 공기:  20,368개 = 93.1%
```

카운터가 있으니 "조용히"는 아니다. 하지만 **숫자가 작은 회색 글씨로 적혀 있고, 운영자는 비전문가다.** 4.5%를 보면서 "다 있는 화면"이라고 읽을 위험은 그대로 있다.

**강제하는 법 — 규칙 4개 (설계 헌법에 넣을 것)**

**규칙 1 — 그리기 함수가 숫자를 리턴하게 만든다 (침묵 대신 물음표).**
```
drawLayer(layer) → 반드시 {총, 그린수} 를 리턴한다
렌더 루프는 리턴값만 모아서 화면에 쓴다
리턴을 안 하면 → 화면에 "??" 가 뜬다
```
개발자가 빼먹었을 때 **아무 일도 안 일어나는 게 아니라 물음표가 뜨게** 만드는 것이 핵심이다. 지금 방식(카운터를 따로 부름)은 빼먹으면 침묵한다.

**규칙 2 — 총계 검산식을 화면에 박는다. 사람 눈이 아니라 산수가 지킨다.**
```
노드 328 = 개념 249 + 계층 가상 66 + 유닛 12 + 미등재 1
간선 22,771 = 공기 21,869 + 관계 587 + 계층 315
합이 안 맞으면 → 빨간 배너 "총계 불일치: 기대 22,771 / 실제 22,756 (−15)"
```
**이 규칙이 있었으면 소집장의 계층 300 vs DB 315를 오늘 아침에 잡았다.**

**규칙 3 — 원천·DB·화면 3지점 대조.** 지금은 DB–화면 2지점만 본다.
```
빌더(파이썬)가 jsonl 을 읽은 직후의 행 수를 DB 에 같이 박는다:
  DB.src = {neuron_edges: 21869, relation_edges: 887, nodes: 249}
화면은 자기가 받은 배열 길이와 DB.src 를 비교하고, 다르면 배너.
```
빌더가 중간에 필터링해서 흘린 것을 잡는 유일한 방법이다. (지금 `build_db()`는 `if e["a"] in idx_of and e["b"] in idx_of`로 **조용히 거른다** — 걸러진 개수를 아무도 안 센다.)

**규칙 4 — 숨긴 이유를 같이 적는다.** 숫자만으로는 운영자가 판단을 못 한다.
```
나쁨:  공기 1,501 / 21,869
좋음:  공기 1,501 / 21,869  — 20,368개는 강도 224 미만이라 접힘 [슬라이더를 왼쪽으로]
```
"성능 때문"인지 "가독성 때문"인지 "데이터가 없어서"인지를 **화면이 구분해서 말해야 한다.** 이 셋은 완전히 다른 문제이고, 지금은 셋 다 똑같이 "안 보임"으로 나타난다.

## 3. 내가 틀렸을 수 있는 지점 (자기 반증)

**1. ★가장 크게 틀렸을 수 있는 것 — "성능은 문제가 아니다"라는 결론 자체가 위험하다.**
이 프로젝트의 사고는 100% 조용한 오작동이었다. 내가 "여유 있다"고 선언하는 순간, **기본 화면이 95.5%를 안 그리고 있다는 사실을 아무도 안 묻게 된다.** 그건 성능 문제가 아니라서 내 관할 밖이지만, 내 결론이 그 질문을 덮는 데 쓰일 수 있다. 그래서 §2-7을 의견서에서 제일 길게 썼다. **내 결론의 올바른 사용법은 "그러니 마음껏 그려라"가 아니라 "그러니 성능을 핑계로 자를 수 없다"이다.**

**2. 기계 한 대에서만 쟀다.** 32코어·32GB·GTX 1080이다. 운영자가 회사 노트북(내장 GPU)에서 열면 Canvas 수치가 3~5배 나빠질 수 있다 [미측정]. 다만 그래도 22,899간선 = 15~25ms 수준이라 **"Canvas로 충분하다"는 결론은 안 뒤집힌다** [추론]. 뒤집히는 건 라벨 상한이다 — 6,000개가 1,500개로 내려갈 수 있다. **LOD의 라벨 예산을 2,000 안전선으로 잡은 게 그래서다.**

**3. Canvas 벤치의 좌표가 랜덤이다.** 실제 그래프는 허브 주변에 선이 겹쳐 같은 픽셀을 수십 번 덧칠한다(오버드로). 밀집 구간의 실제 fill rate는 내 측정보다 나쁠 수 있다 [미측정]. 다만 실제 `draw()`를 그대로 호출한 측정(4.95ms)도 같은 결론이라 두 경로가 서로를 받쳐준다.

**4. 브라우저가 Claude 내장 브라우저다.** 운영자의 Edge/Chrome과 GPU 합성 정책·`file://` 정책이 다르다(§2-5에서 실제로 달랐다). 특히 **`file://` 결론은 내 측정이 아니라 추론에 기대고 있다.**

**5. `<script src>` 방안(b)을 측정하지 못했다.** 표준 동작상 된다고 믿지만 [추론], 프리뷰 도구가 `file://`을 못 띄워 확인 못 했다. 만약 이걸 채택하려는 위원이 있다면 **채택 전에 운영자 브라우저에서 직접 더블클릭해서 확인해야 한다.** 내 의견서를 근거로 삼지 마라.

**6. 개념트리 리플로우 13.9ms와 내 합성 벤치 6,000박스 348ms가 안 맞는다.** 개념트리는 2,679박스에 13.9ms인데, 내 벤치는 6,000박스에 348ms다 — 박스당 비용이 25배 차이 난다. 내 벤치의 박스가 padding·border가 있어 더 무겁기 때문으로 보이지만 [추론], **박스당 정확한 단가는 못 냈다.** 그래서 "6,000개 상한"은 보수적으로(=내 무거운 벤치 기준으로) 잡은 값이다.

## 4. 다른 위원과 갈릴 것 같은 지점

**① "간선 22,756개는 너무 많다 / 공기를 줄이자"**
→ **반대. 성능 근거로는 성립 안 한다.** 실측 4.95ms(202fps)다. 줄이자는 이유가 성능이면 근거가 없고, 가독성이면 그건 시각언어 위원(F2) 관할이다. 그리고 헌법상 처분은 **삭제가 아니라 `kind:"공기"` 강등**이다. 내 입장: **줄이는 건 좋다. 단 "무거워서"라고 쓰지 마라 — 그건 사실이 아니고, 사실이 아닌 이유는 나중에 검증되지 않는다.**

**② "파일을 쪼개고 fetch로 불러오자"**
→ **반대.** `file://`에서 보장되지 않는다(§2-5). 인라인이 20MB까지 실측으로 안전하다. 지금 전체 원천이 20.86MB이고 그중 65%가 `paras_all`인데, 화면이 문단 전문을 다 들고 있을 이유가 없다(포인터만 있으면 된다). **필요량은 1MB대다.** 쪼갤 문제 자체가 없다.

**③ "WebGL로 가자 / 미래를 대비해 지금 갈아타자"**
→ **반대.** 얻는 것 4.95ms → 0.005ms. 치르는 것: 굵기 가변 불가(축② 사망), 텍스트 불가(라벨을 Canvas로 겹쳐야 함), 셰이더 실패가 **까만 화면 + 에러 없음**. 마지막 항목이 결정적이다 — 이 프로젝트가 유일하게 감당 못 하는 실패 유형이다.

**④ "5개 화면을 하나로 합치자"**
→ **조건부 찬성.** 합치면 6.99MB이고 그건 0.5초 안에 열린다. **단 개념트리를 DOM인 채로 합치면 안 된다** — 105,463요소가 같은 문서에 들어오는 순간 그 문서의 **모든** 리플로우가 그 비용을 낸다(창 크기만 바꿔도). 합치려면 개념트리를 데이터 + 가상스크롤로 바꿔야 하고, 그건 자산 폐기가 아니라 렌더러 교체다(빌더 보존, 되돌리기 가능).

**⑤ "지식망을 새로 만들자 / 갈아엎자"**
→ **강하게 반대.** 운영자가 "그거 날릴 게 아닌 것 같음"이라고 지목한 파일이고, **성능 관점에서 이미 정답이다.** 배치 스트로크(stroke 1,365회로 24,160선분), 임계 슬라이더, `counts()` 카운터 — 세 개 다 제대로 돼 있다. 이번 통합에서 내가 본 자산 중 **고칠 게 가장 적은 파일**이다.

**⑥ (예상되는 반론) "네 측정은 게이밍 PC에서 한 거라 못 믿겠다"**
→ 맞는 지적이다. 그런데 **그 PC가 운영자 본체다**(측정 환경 = Windows 11 Pro 10.0.26200, 소집장이 명시한 그 기기). 운영자가 다른 기기에서도 본다면 재측정이 필요하다 — 그때 쓸 수 있게 §2 표를 전부 재현 가능한 형태(개수·ms)로 남겼다.

## 5. 하지 말아야 할 것 (내 관점의 금지 목록)

1. **성능을 이유로 간선을 삭제하지 마라.** 22,899개 = 4.95ms다. 성능 근거는 존재하지 않는다.
2. **조용한 기본값을 두지 마라.** 지금 기본 화면은 간선의 **4.5%**만 그린다. 감춰도 되지만 **감췄다고, 왜 감췄는지 화면에 써라.**
3. **개념트리를 DOM인 채로 통합 문서에 합치지 마라.** 105,463요소가 들어오면 창 크기 변경 한 번이 초 단위 정지가 된다.
4. **"전부 펼치기" 버튼을 만들지 마라.** 2,679개 펼치면 1.9초 정지 + 1,391,843px. 만들려면 상한(예: 200개)과 "N개 중 M개만 펼침" 표시를 함께.
5. **fetch/XHR에 의존하지 마라.** `file://`에서 보장되지 않는다. 인라인을 유지하라.
6. **라벨을 전부 그리지 마라.** 22,756개 = 38.33ms로 프레임 예산을 혼자 먹는다. **상한 6,000 · 안전 2,000.**
7. **shadowBlur(빛)를 간선 전량에 걸지 마라.** 21,869개 환산 ≈ 14ms. 축⑤(연결 빛의 강도)를 글로우로 표현하려면 **강조된 수백 개에만.** 나머지는 알파(투명도)로 — 알파는 배치가 되니까 공짜다.
8. **WebGL·SVG로 갈아타지 마라.** SVG는 갱신 50.8ms로 이미 지금보다 10배 느리고, WebGL은 조용히 까맣게 실패한다.
9. **OneDrive 탈수화를 방치하지 마라.** HTML 5개 전부 `ReparsePoint`인데 `P`(항상 이 장치에 유지)가 없다. **폴더에 "항상 이 장치에 유지"를 걸어라** — 안 그러면 언젠가 "오프라인 더블클릭" 헌법이 조용히 깨진다.
10. **파이프라인이 화면 5개(6.99MB)를 매번 전량 재작성하는 구조를 키우지 마라.** OneDrive는 HTML을 블록 델타로 동기화하지 않는다 → 갱신 1회 = 7MB 업로드 [추론]. 20MB 통합본이 되면 갱신 1회 = 20MB다.
