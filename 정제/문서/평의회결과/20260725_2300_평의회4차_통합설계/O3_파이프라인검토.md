### 🔴 D4. 판정 기준이 mtime인데, **이 폴더의 mtime은 이미 초 단위로 잘려 있고 일부만 잘려 있다**

**실측:** P0 배치 산출물 180개 중 **86개(47.8%)의 mtime 소수점이 정확히 .000**이다.
로컬 NTFS 쓰기는 100ns 해상도라 소수점이 0으로 딱 떨어질 확률이 사실상 0이다 → **어딘가에서 초 단위 절삭이 일어난다.**

`_현황판` 안에서도 갈린다:

```
정수초(.000)  paras_all.jsonl 08:32:39.000 · posts_all 08:32:39.000 · stats.json 08:32:39.000
              현황판.html 08:32:39.000 · concept_tree.json 09:08:10.000 · 개념트리.html 09:08:10.000
              별칭_판정.json 14:35:19.000 · lint_aliases.py 14:34:32.000 · build_concept_tree.py 08:19:07.000
소수점 살아있음  개념지도.html 22:53:20.425 · relation_edges 22:53:41.157 · neuron_nodes 22:54:13.590
              뉴런망.html 22:54:13.702 · 지식망.html 22:55:59.753 · 파이프라인.py 22:54:41.776
```

**옛 파일은 잘려 있고 방금 쓴 파일은 안 잘려 있다.** 원인이 OneDrive 동기화 왕복인지 복사 도구인지는 [미측정]이지만,
**"시간이 지나면 mtime이 초 단위로 뒤로 이동한다"**는 사실 자체는 [실측]이고, 판정에 미치는 영향은 원인과 무관하다.

**여기서 두 가지가 깨진다:**
- **해상도 1초.** 판정식이 `newest(ins) > oldest(outs)` **순수 부등호**라 같은 초에 쓰인 입력·출력은 "최신"이다.
- **절삭은 시간을 뒤로 옮긴다.** 지금 "낡음"인 단계가 입력만 절삭되면 **저절로 "최신"으로 뒤집힌다.**

**재현:** 입력과 출력이 같은 초 안에 기록된 뒤 입력 파일만 동기화 절삭 → 낡음 판정이 스스로 사라진다.
(반대 방향은 무해한 재실행이라 눈에 안 띈다. **위험한 방향만 조용하다.**)

### 🔴 D5. 입력이 **지워지거나 내용만 바뀌면** 못 잡는다

- **삭제 무감지.** `newest(ins)`는 최대값이라, glob 입력에서 파일이 사라져도 값이 안 변한다. 배치 하나를 지워도 "최신".
- **타임스탬프 보존 복사가 지뢰다.** `robocopy`·PowerShell `Copy-Item`은 기본으로 원본 시각을 보존한다.
  스크래치패드에서 03:00에 만든 배치를 09:00에 손으로 복사해 반입하면 그 파일의 mtime은 **03:00**이 되고,
  08:32에 만들어진 `paras_all.jsonl`보다 **낡아 보인다** → ① = 최신 → **새 배치가 통합본에 영원히 안 들어간다.**
  (`_tools\p0_import.py`:29는 `shutil.copy`라 이 경로는 안전하다. 위험한 건 손복사 경로인데,
  **배치 86개가 이미 절삭된 mtime을 갖고 있다는 건 손복사 경로가 실재한다는 뜻이다.**)
- **내용만 바뀌면 못 잡는다.** 크기·줄 수·해시를 아무도 안 본다. 파일을 되돌려도(구버전 복원) mtime만 새로우면 "최신".

이 프로젝트의 사고 이력이 정확히 이 모양이다 — **R7: 석우당 130편이 사라졌는데 로그는 `🏁 전량 종료 847편`.**

**재현:** ④ 실행 중 `neuron_edges.jsonl`(2,180,895B · 21,869줄)을 쓰는 도중에 Ctrl+C / 세션 한도 /

⑦⑧이 잘린 간선 위에 화면과 계기판을 그린다.
(⑦의 `assert len(edges) > 1000`은 1,000줄 미만만 잡는다. **15,000줄에서 잘리면 그대로 통과한다.**)

**물증 [실측] — 지금 ⑥의 두 산출물이 5분 44초 벌어져 있다:**
```
data\relation_edges.jsonl   22:53:41.157

```
`build_relation_edges.py`는 659행에서 relation_edges를, 681행에서 node_layers를 **연속으로** 쓴다(사이에 무거운 계산 없음).

원인은 [추론](쓰기 중 실패 또는 부분 실행 — 검토 중 다른 담당이 이 파일을 고치고 있어 단정 불가).

### 🔴 D7. 입력이 하나도 안 잡히면 **에러 없이 통째로 건너뛴다**


  `build_neuron_map.py:180`은 NFC/NFD 양쪽을 찾는데 **파이프라인의 `resolve()`는 안 한다.**
  이 프로젝트는 NFC/NFD 파일명 사고를 이미 한 번 겪었다.

### Q5. 더 나은 설계가 있나 — **제약(비전문가·더블클릭·파이썬 표준 라이브러리만) 안에서**

Makefile도, 해시 캐시 프레임워크도 필요 없다. **8단계 선형 파이프라인에 의존성 그래프는 과잉 설계다.**
필요한 건 4가지고, 전부 표준 라이브러리로 된다.

**① mtime을 버리고 매니페스트를 써라 (`hashlib` — 의존성 0)**
각 단계 성공 직후 `data\_manifest\<단계>.json`에 기록:
```json
{"done": true, "at": "...", "script_sha": "...",
 "inputs":  [{"p": "...", "size": 0, "sha": "..."}],
 "outputs": [{"p": "...", "size": 0, "lines": 0, "sha": "..."}]}
```
낡음 판정 = **현재 입력 해시 ≠ 매니페스트 기록 해시** (+ `script_sha` 불일치 = D1 해결).
- mtime을 안 쓰니 OneDrive 절삭(D4)·타임스탬프 보존 복사(D5)·기기 시계차에 **면역**

- **`done: true`가 없으면 무조건 낡음** → 중단된 실행이 "최신"으로 굳는 사고(D6)가 원천 차단
- 비용: 스냅샷 57.9MB 읽기가 0.7초 [실측] → SHA 추가해도 1초 미만 [추론]. 부담 없음.

**② 실행 후 자기검사 3줄 (D8·D11 동시 해결)**
단계 실행 **전후로 `_현황판` 전체 파일의 (경로, size, mtime)을 스냅샷**해서 비교:
- 선언한 산출물이 안 바뀌었으면 → **거기서 멈춰라** ("돌았는데 안 바뀌었다"는 실패다)
- 선언 안 한 파일이 바뀌었으면 → **미선언 산출물로 고발** (이걸 넣었으면 `개념마커_적중률.md`가 즉시 잡혔다)
- 같은 방식으로 **선언한 입력을 실제로 읽었는지**도 볼 수 있다(atime은 못 믿으니, 대신 각 빌더 상단에

  → 사람이 손으로 적은 선언이 이미 6/8 틀렸다. **선언을 코드 옆으로 옮기는 것이 근본 해법이다.**

**③ 회귀 임계 (R7 재발 방지)**
`build_neuron_map.py`는 이미 `_prev_counts()`로 회귀 방어를 한다 — 그걸 **파이프라인 층으로 올려라.**

**④ 운영자 접점 (D14·D15)**
- `전체갱신.bat` 신설: `python 파이프라인.py --all` → `pause` → `start "" "허브.html"`
- **`현황판_갱신.bat`은 지우지 말고 내용만 파이프라인 호출로 바꿔라** — 운영자 근육기억이 거기 있다(자산 폐기 금지 원칙).

  비전문가에게 3분 침묵은 "멈췄다"이고, 그때 창을 닫으면 D6이 된다.

## 5. 내가 틀렸을 수 있는 지점 (자기 반증)

1. **파이프라인을 실행하지 않았다.** `--all`의 성공 여부·소요 시간·메모리는 전부 [추론]/[미측정]이다.
   특히 ⑦의 미확인 끝점 검사가 `--all`에서 어떻게 도는지는 코드로만 봤다. 내가 놓친 방어가 있을 수 있다.
2. **mtime 절삭의 원인을 안 밝혔다.** 86/180이 정수초라는 건 [실측]이지만, 그게 OneDrive인지 robocopy인지
   특정 도구인지는 [미측정]이다. 동기화 전후를 직접 관측하지 않았다.
   다만 **원인이 무엇이든 "일부 파일만 초 단위로 잘려 있다"는 사실과 그 판정 영향은 동일**하다.
3. **⑥의 5분 44초 격차는 내 관측 시점의 아티팩트일 수 있다.** 소집장이 경고한 대로 다른 담당 3인이
   지금 같은 폴더를 고치고 있고, 실제로 `build_relation_edges.py`가 내 검토 중에 바뀌었다.
   원인 판단은 [추론]으로 남긴다. **다만 "같은 실행에서 나왔는지 검사가 없다"는 건 원인과 무관하게 [실측]이다.**
4. **D5의 "타임스탬프 보존 복사" 시나리오는 반쪽 검증이다.** `p0_import.py`는 `shutil.copy`라 안전하다.
   손복사 경로가 실재한다는 근거는 "배치 86개가 이미 절삭된 mtime을 갖고 있다"는 정황이지, 재현이 아니다.
5. **가장 크게 틀렸을 수 있는 지점:** 나는 이 파일을 "부수라"는 임무로 읽었다.
   **부술 게 많았다는 사실이 이 파일이 나쁘다는 뜻은 아니다** — 없는 것보다 100배 낫다.
   ⑦의 방어 코드(미확인 끝점 exit 1, 계층 간선 100 미만 exit 1)는 **이 프로젝트에서 내가 본 가장 좋은 코드**다.
   문제는 그 수준이 파이프라인 층에는 안 올라왔다는 것이다.

1. **⛔ mtime 판정을 이대로 두고 운영자에게 넘기지 마라.** 86/180이 이미 잘려 있다. 판정의 전제가 깨져 있다.

7. **⛔ 새 단계를 추가할 때 `inputs`를 손으로 적고 검사 없이 믿지 마라.** 이미 6/8이 틀렸다.
